ADS-B Encoder Library (<tt>encoder.c</tt>) – Software Requirements Specification

1. Purpose

The purpose of the ADS-B Encoder Library is to generate valid ADS-B Out DF17 Extended Squitter messages compliant with the requirements defined in RTCA DO-260B and ICAO Annex 10.

The encoder shall be implemented as a standalone ANSI C library independent from any specific hardware platform, operating system, or radio transceiver.

The library shall provide deterministic generation of ADS-B messages from navigation and aircraft state data and serve as the core component of the proposed low-cost ADS-B Out architecture.

2. Design Objectives

The encoder shall:

  • Be portable across embedded and desktop platforms.
  • Avoid dynamic memory allocation.
  • Avoid operating system dependencies.
  • Use fixed-size data structures.
  • Produce deterministic outputs for identical inputs.
  • Be suitable for unit testing and offline verification.
  • Support future integration into STM32-based avionics hardware.

3. Supported Message Types

The initial implementation shall support the following ADS-B message categories:

3.1 Aircraft Identification

Message:

  • DF17
  • Type Code 1–4

Fields:

  • ICAO Address
  • Aircraft Callsign

3.2 Airborne Position

Message:

  • DF17
  • Type Code 9–18

Fields:

  • ICAO Address
  • Barometric Altitude
  • CPR Latitude
  • CPR Longitude
  • Odd/Even Frame Indicator

The encoder shall support generation of both:

  • Even CPR frame
  • Odd CPR frame

3.3 Airborne Velocity

Message:

  • DF17
  • Type Code 19

Fields:

  • Ground Speed
  • Track Angle
  • Vertical Rate

4. Input Requirements

4.1 ICAO Address

Type:

uint32_t

Range:

0x000000 – 0xFFFFFF

Only the least significant 24 bits shall be used.

4.2 Callsign

Maximum length:

8 characters

Allowed characters:

A-Z
0-9
Space

The encoder shall reject unsupported characters.

4.3 Latitude

Type:

double

Range:

-90° ≤ latitude ≤ +90°

4.4 Longitude

Type:

double

Range:

-180° ≤ longitude ≤ +180°

4.5 Altitude

Type:

int32_t

Unit:

feet

Range:

-1000 ft to 60000 ft

4.6 Velocity

Ground Speed:

knots

Track:

degrees

Vertical Rate:

feet/minute

5. Output Requirements

The encoder shall generate complete DF17 messages containing:

112 bits
14 bytes
28 hexadecimal characters

Output format:

uint8_t frame[14];

The generated message shall include:

  • Downlink Format
  • Capability Field
  • ICAO Address
  • ME Field
  • CRC / Parity

6. CPR Encoding Requirements

The encoder shall implement:

  • Global CPR encoding
  • Even frame generation
  • Odd frame generation

The implementation shall follow:

RTCA DO-260B
ICAO Annex 10 Volume IV

The encoder shall correctly calculate:

  • Latitude index
  • Longitude index
  • NL(latitude)
  • CPR compressed coordinates

7. CRC Requirements

The encoder shall implement the Mode S CRC-24 algorithm.

Polynomial:

0xFFF409

The CRC shall be computed over the first 88 bits of the DF17 message.

The resulting parity field shall occupy the final 24 bits.

9. Determinism Requirements

For identical inputs:

Input A → Output X
Input A → Output X
Input A → Output X

The generated frame shall always be identical.

No randomization shall be used.

10. Verification Requirements

The implementation shall be validated against pyModeS.

Validation activities shall include:

V1 – CRC Verification

Objective:

Verify CRC consistency.

Acceptance Criterion:

100% match with pyModeS

V2 – Callsign Verification

Objective:

Verify Aircraft Identification messages.

Acceptance Criterion:

Decoded callsign equals encoded callsign

V3 – CPR Verification

Objective:

Verify position encoding.

Method:

  • Encode position using encoder.c
  • Decode using pyModeS

Acceptance Criterion:

Position error < 30 m

for all test vectors.

V4 – Velocity Verification

Objective:

Verify velocity encoding.

Acceptance Criterion:

Decoded velocity equals encoded velocity

within ADS-B quantization limits.

11. Coding Requirements

The implementation shall:

  • Follow ANSI C99.
  • Compile without warnings using:
gcc -Wall -Wextra -Werror
  • Avoid compiler-specific extensions.
  • Avoid dynamic memory allocation.
  • Avoid recursion.

12. Future Extensions

The architecture shall permit future addition of:

  • SIL
  • SDA
  • NIC
  • NACp
  • Operational Status Messages
  • Surface Position Messages
  • GNSS Integrity Monitoring
  • Integrated Built-In Test Reporting

without modification of existing encoder interfaces.
