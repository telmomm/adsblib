# adsblib developer documentation

This folder documents *why* and *where* adsblib is going, for contributors
and maintainers. It complements, but is distinct from, the generated API
reference:

- **User-facing API docs** — generated by Doxygen from `adsblib.h`, built
  and published by CI (`.github/workflows/docs.yml`); not stored in this
  repository. See the root [`README.md`](../README.md#documentation).
- **Developer docs (this folder)** — mission/scope, architecture,
  capability roadmap, and the record of significant design decisions.
  These are written by hand and evolve with the project.

## Contents

| Document | Purpose |
| --- | --- |
| [`MISSION.md`](MISSION.md) | Mission, vision, and explicit in/out of scope |
| [`ARCHITECTURE.md`](ARCHITECTURE.md) | Current module layout and the target architecture |
| [`ROADMAP.md`](ROADMAP.md) | Capability roadmap: what adsblib does today vs. what it's building toward |
| [`JOSS_ROADMAP.md`](JOSS_ROADMAP.md) | Separate, submission-specific roadmap for a JOSS paper (history, evidence-of-use, review checklist) |
| [`decisions/`](decisions/) | Architecture Decision Records (ADRs) — the "why" behind constraints that aren't obvious from reading the code |

## Why keep a roadmap *and* a JOSS roadmap?

They answer different questions. `ROADMAP.md` is about what the *library*
should be capable of — closing spec-coverage gaps, adding real technical
capabilities like signal synthesis. `JOSS_ROADMAP.md` is about what a
*paper submission* to JOSS additionally requires — commit history
distribution over time, evidence of research use, a `paper.md`. A library
can be technically excellent and still not be ready for JOSS (not enough
elapsed history), or vice versa. Keeping them separate avoids conflating
"is the software good" with "is the submission ready."

## Writing an ADR

Add a new decision under `decisions/` when a choice constrains future work
in a way that isn't obvious from the code alone — e.g. a scope boundary, a
tradeoff between two designs, or a constraint (like "no dynamic
allocation") that someone could otherwise accidentally violate in a later
PR. Use [`decisions/0000-template.md`](decisions/0000-template.md) as a
starting point and number sequentially.
