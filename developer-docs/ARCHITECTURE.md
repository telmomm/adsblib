# Architecture

## Current layout

```
adsblib/
├── adsblib.h            Public API — types, status codes, function
│                         declarations. The only header consumers include.
├── adsblib.c             Implementation. Single translation unit.
│                         No dynamic allocation, no dependencies beyond
│                         <math.h>/<stdint.h>/<stdbool.h>/<string.h>.
├── validation/
│   ├── encoder_validation.ipynb   Cross-checks encoder output against
│   │                               pyModeS (independent reference decoder).
│   └── requirements.txt
├── docs/                 Doxygen HTML output. Generated by CI
│                         (.github/workflows/docs.yml), not committed.
└── developer-docs/       This folder.
```

Everything the core exposes is declared in `adsblib.h` and defined in
`adsblib.c`. There is currently no build system beyond direct `cc`
invocations (see the root [`README.md`](../README.md#building)) — the
whole core is meant to be usable by dropping two files into another
project.

## Target layout

As the [roadmap](ROADMAP.md) is executed, new capabilities are added as
**separate, optional compilation units** rather than growing
`adsblib.c`. The core keeps its current guarantees (no allocation,
`libm`-only, single TU) regardless of what else exists in the repo.

```
adsblib/
├── adsblib.h / adsblib.c          Core encoder (unchanged guarantees)
├── adsblib_signal.h / .c          [planned] PPM/Manchester modulation:
│                                   DF17 frame -> IQ sample buffer at a
│                                   configurable sample rate. Depends on
│                                   the core; may use floating-point
│                                   sample buffers supplied by the caller.
├── adsblib_scenario.h / .c        [planned] Multi-frame scenario
│                                   generation: aircraft state evolving
│                                   over time -> a sequence of correctly
│                                   spaced, correctly varying frames.
│                                   Depends on the core.
├── examples/                      [planned] End-to-end programs per
│                                   capability (identification, position,
│                                   velocity, signal, scenario).
├── tests/                         [planned] Unit tests (Fase 1 of
│                                   JOSS_ROADMAP.md), independent of the
│                                   pyModeS notebook.
└── ...
```

### Module dependency direction

```
   adsblib_scenario  ──┐
                        ├──>  adsblib (core)
   adsblib_signal    ──┘
```

Optional modules depend on the core; the core never depends on them. A
project that only needs frame bytes links only `adsblib.c` and never pulls
in the signal or scenario modules' dependencies.

### Why not just one bigger `adsblib.c`?

Because the core's "no dynamic allocation, `libm` only" guarantee is a
selling point for embedded/experimental-avionics users specifically. IQ
signal buffers and scenario state are legitimately harder to make
allocation-free in general (arbitrary sample counts, arbitrary aircraft
counts), so folding them into the core would either weaken that guarantee
for everyone, or force awkward fixed-capacity APIs onto users who don't
need them. Splitting into optional modules lets each module make the
allocation tradeoff that fits its own problem (e.g. the signal module can
expose a "how many samples will this need" sizing function so the *caller*
allocates, keeping the module itself allocation-free while still being
practical to use). See
[`decisions/0005-optional-modules-boundary.md`](decisions/0005-optional-modules-boundary.md).

## Data flow (target end state)

```
adsb_identification_t  ─┐
adsb_position_t         ├─> adsb_encode_*()  ─>  112-bit DF17 frame
adsb_velocity_t         │      (adsblib core)         │
...                    ─┘                              │
                                                          ▼
                                          adsb_signal_modulate()
                                            (adsblib_signal, planned)
                                                          │
                                                          ▼
                                              IQ sample buffer
                                          (caller-owned, ready for SDR
                                           TX or receiver test injection)

adsb_scenario_step()  (adsblib_scenario, planned)
   generates a sequence of the structs above from an evolving
   aircraft state, which then feed the same adsb_encode_*() path.
```
